# MockSvr

AI-powered API mock server. Phases 1-11 of the roadmap: core server, endpoint
registry, dynamic routing, response generation (AI + faker + static fallback),
request variable injection, stateful resources, and OpenAPI import.

## Stack

- Go 1.26+
- Fiber v3
- Bun ORM
- PostgreSQL
- golang-migrate (embedded migrations)
- zerolog
- Viper
- uberfx (dependency injection)

## Requirements

- Go 1.26+ (toolchain auto-downloads via `GOTOOLCHAIN=auto`)
- Docker + Docker Compose (for the local PostgreSQL)

## Run

```sh
docker compose up -d postgres   # start PostgreSQL
make run                        # apply migrations + start the server
```

Configuration is read from `configs/config.yaml` and overridable with
`MOCKSVR_*` environment variables. Copy `.env.example` to `.env` for defaults.

## Tests

```sh
make test   # unit tests
```

Repository integration tests require PostgreSQL and are skipped unless
`MOCKSVR_TEST_DATABASE_URL` is set:

```sh
MOCKSVR_TEST_DATABASE_URL=postgres://mocksvr:mocksvr@localhost:5432/mocksvr?sslmode=disable make test-integration
```

## API

All responses use a consistent envelope.

Success:

```json
{ "success": true, "data": {} }
```

Failure:

```json
{ "success": false, "error": { "code": "...", "message": "..." } }
```

### Endpoint registry

| Method | Path                          | Description                |
| ------ | ----------------------------- | -------------------------- |
| GET    | /health                       | Health check               |
| GET    | /api/v1/endpoints             | List endpoints (paginated) |
| POST   | /api/v1/endpoints             | Create endpoint            |
| GET    | /api/v1/endpoints/:id         | Get endpoint               |
| PUT    | /api/v1/endpoints/:id         | Replace endpoint           |
| DELETE | /api/v1/endpoints/:id         | Delete endpoint            |
| GET    | /api/v1/endpoints/:id/versions| List endpoint versions     |
| GET    | /api/v1/endpoints/:id/history | List request history       |
| POST   | /api/v1/imports/openapi       | Import an OpenAPI document  |
| POST   | /api/v1/imports/postman       | Import a Postman collection |

Example create:

```sh
curl -X POST http://localhost:8080/api/v1/endpoints \
  -H 'Content-Type: application/json' \
  -d '{"method":"post","path":"/users","prompt":"create a user and return it"}'
```

Creating or updating an endpoint always records a new `EndpointVersion`
(version 1 on create, then a bump whenever the prompt changes). Create accepts
`request_schema` (a JSON Schema string for the request body); update accepts it
as an optional string, where `""` clears the schema and omitting it keeps the
current one.

## Dynamic routing

Registered mock endpoints are served without a restart: the router resolves
every request against the database and generates a response on the fly.
Routes outside the control plane (`/health`, `/api/v1/*`) are treated as mock
endpoints.

```sh
curl -X POST http://localhost:8080/api/v1/endpoints \
  -H 'Content-Type: application/json' \
  -d '{"method":"get","path":"/users/:id","prompt":"return a user by id"}'

curl http://localhost:8080/users/42
# => {"endpoint":"/users/:id","message":"...","method":"GET","params":{"id":"42"},"query":{}}
```

- Path patterns support `:param` segments; static segments take precedence
  over parameters when both match (`/users/me` beats `/users/:id`).
- Only `status: active` endpoints are served.
- Responses are generated by `internal/generator`. When an AI provider is
  configured, the generator loads the endpoint's stored JSON Schema, embeds it
  in the prompt, asks the model for a response, and validates it against the
  schema (retrying once on failure). If AI is disabled or unreachable, the
  schema-driven **faker generator** fills the stored schema with realistic
  values (email, name, phone, address, credit card, currency, country, dates,
  and more); if no schema is stored, the deterministic stub that echoes the
  request context is the final fallback. Composed schemas are supported: `allOf`
  members are merged and `oneOf`/`anyOf` pick their first member when filling.
- Prompts support request variables. Before the prompt reaches the provider,
  placeholders are replaced with values from the incoming request:

  ```
  {{path.id}}           path parameter
  {{query.country}}     query parameter
  {{body.email}}        field of the JSON request body (dot paths like
                        {{body.user.name}} are supported)
  {{headers.auth}}      request header (case-insensitive)
  {{cookies.session}}   request cookie
  ```

  Names are case-insensitive and missing values render as an empty string.
- Endpoints can declare a **request schema** (`request_schema`) — a JSON Schema
  describing the expected request body. Before any response is generated, the
  incoming body is validated against it; a non-conforming or missing body is
  rejected with `400 {"error":{"code":"VALIDATION_ERROR",...}}`, so an endpoint
  that requires `{"email": {"type":"string","format":"email"}}` refuses
  `{"email":"not-an-email"}`. Formats like `email`, `uuid`, and `date-time` are
  enforced. An empty schema disables validation for that endpoint.
- Every served request is recorded and visible via
  `GET /api/v1/endpoints/:id/history`.

## Stateful endpoints

Endpoints flagged `"stateful": true` act as persistent mock APIs. A `POST`
creates a resource, and the same object is returned by `GET`, updated by
`PUT`/`PATCH`, and removed by `DELETE` on the corresponding item path:

```sh
curl -X POST http://localhost:8080/api/v1/endpoints \
  -H 'Content-Type: application/json' \
  -d '{"method":"post","path":"/users","prompt":"create a user","stateful":true}'

# repeat for GET/PUT/PATCH/DELETE /users/:id with "stateful":true

curl -X POST http://localhost:8080/users -H 'Content-Type: application/json' -d '{"email":"a@b.co"}'
# => {"email":"a@b.co","id":"<uuid or ai id>",...}  201

curl http://localhost:8080/users/1          # 200, returns the same object
curl -X PATCH http://localhost:8080/users/1 -H 'Content-Type: application/json' -d '{"name":"Ada"}'
curl -X DELETE http://localhost:8080/users/1 # 204
curl http://localhost:8080/users/1          # 404
```

- Resources are keyed by the endpoint's **collection path** (the path pattern
  without its trailing `:param`) plus the resource id from the path, so
  `POST /users`, `GET /users/:id`, `PUT /users/:id`, and `DELETE /users/:id`
  share one namespace.
- On `POST` the resource body is generated through the normal pipeline (AI +
  schema validation, with the static fallback). Its id is taken from the
  body's `id` field when present, otherwise a UUID is generated and injected.
- `PUT` replaces the stored object (preserving the id from the path), `PATCH`
  deep-merges the request body into it, `DELETE` removes it, and unknown ids
  return `404 {"error":"resource not found"}`. Duplicate `POST` ids return
  `409`.
- Resources are stored in PostgreSQL (`mock_resources`), so they survive
  server restarts. Endpoints without a trailing `:param` only support the
  create operation; other requests fall through to normal generation.

## OpenAPI import

Existing APIs can be bootstrapped from their spec. `POST /api/v1/imports/openapi`
accepts a Swagger 2.0 or OpenAPI 3.x document in **JSON or YAML**, either as
the raw request body or as a multipart upload in the `file` field:

```sh
curl -X POST http://localhost:8080/api/v1/imports/openapi \
  -H 'Content-Type: application/json' \
  --data @openapi.json
# => { "success": true, "data": { "parsed": 4, "created": 4, "skipped": 0, "endpoints": [...] } }

curl -X POST http://localhost:8080/api/v1/imports/openapi \
  -F file=@swagger.yaml
```

Every operation becomes a registry endpoint:

- OpenAPI path templates become router parameters: `/users/{id}` →
  `/users/:id`.
- The operation **summary** and **description** become the endpoint's prompt,
  so imported endpoints generate richer responses.
- The JSON Schema of the first 2xx response is resolved against the document's
  components/definitions and stored on the endpoint's first version. With AI
  disabled, the faker generator immediately serves schema-conforming data.
  Schemas that fail JSON Schema validation (e.g. unresolvable `$ref`) are
  stored without a schema instead of failing the import.
- An operation's `requestBody`/`body` JSON Schema is stored as the endpoint's
  `request_schema` (first JSON media type wins, `$ref`s resolved), so imported
  endpoints validate incoming bodies the same way. The schema is dropped with a
  warning if it fails validation.
- Re-importing is idempotent: operations whose method + path already exist are
  reported as `skipped`, not recreated.

## Postman import

Existing Postman collections bootstrap the registry the same way.
`POST /api/v1/imports/postman` accepts a **Collection v2.0/v2.1 JSON** document
(raw body or multipart `file` field):

```sh
curl -X POST http://localhost:8080/api/v1/imports/postman \
  -H 'Content-Type: application/json' \
  --data @collection.postman_collection
curl -X POST http://localhost:8080/api/v1/imports/postman -F file=@collection.json
```

Every request in the collection (folders walked recursively) becomes a mock
endpoint:

- **Methods and paths** come from `request.method` and `request.url`.
  `url.path` (array or string) is used when present, otherwise the path is
  extracted from `url.raw` (scheme and host stripped). Postman path templates
  already use router syntax (`/users/:id`), and `{{variable}}` placeholders are
  converted to `:param` — `{{baseUrl}}/users/{{id}}` → `/users/:id`.
- **Prompts** combine the request name and description, so imported endpoints
  generate richer responses.
- **Requests**: when `request.body.mode` is `raw` and the body is JSON, a JSON
  Schema is inferred from the sample and stored as `request_schema`, so the
  endpoint validates incoming bodies (missing fields → `400`).
- **Responses**: a JSON Schema is inferred from the saved example responses,
  preferring the first 2xx example with a JSON body. With AI disabled, the
  faker generator immediately serves schema-conforming data.
- Re-importing is idempotent, same as OpenAPI.

## Architecture

```
Handler        internal/endpoint  HTTP concerns only
    ↓
Service        internal/endpoint  business logic, validation, versioning
    ↓
Repository     internal/endpoint  persistence (Bun ORM)
    ↓
Database       PostgreSQL
```

- `cmd/server` — entry point, uberfx wiring, graceful shutdown
- `internal/api` — response envelope helpers
- `internal/config` — Viper config + zerolog setup
- `internal/database` — Bun connection pool + golang-migrate runner
- `internal/endpoint` — endpoint feature (dto, repository, service, handler)
- `internal/generator` — mock response generation (AI pipeline, schema-driven faker, stateful storage, static fallback)
- `internal/importer` — OpenAPI + Postman imports (Swagger 2.0/OpenAPI 3.x, Postman Collection v2)
- `internal/middleware` — request logging
- `internal/models` — shared domain models
- `internal/router` — Fiber app assembly, routes, dynamic endpoint resolver
- `internal/state` — persistent resource store for stateful endpoints
- `migrations` — embedded SQL migrations

Migrations run automatically at startup. Create an endpoint and it is served
from the database with no restart.
